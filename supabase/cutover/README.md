# 本番切替の手順（公開アクセス遮断・共有リンク再発行）

各SQLは Supabase の SQL Editor に、このリポジトリの最新ファイルから貼り付ける（旧クローンのファイルは使わない）。秘密値はチャット・Issue・PRに書かない。

## 事前（アプリは止めずにできる）
1. Supabase Auth で管理者アカウントを作成し、Authentication の設定で一般の新規登録（Sign ups）を無効にする。
2. Vercel の Production 環境変数に `SUPABASE_SERVICE_ROLE_KEY`、`ADMIN_EMAIL`（管理者のメールアドレス）、任意で `CRON_SECRET` を登録する。
3. 既存のポリシー・権限を Supabase の SQL Editor で読み取り確認する（列追加前は `verify.sql` のG欄が存在せず、そのまま実行するとエラーになる）。
4. `01_additive.sql` を実行する（列・トリガーの追加のみ。現行アプリはそのまま動く）。その後 `verify.sql` を実行して切替前の状態を記録する。
5. 外注者へ停止時間と、停止中の連絡方法（下記）を伝える。

## 当日（停止時間の目安: 30〜60分）
1. 管理画面から全データJSONとCSVのバックアップを取得し、件数を画面と照合する。
2. PR #8〜#10 と PR-4（本PR）を順にマージし、Vercel の本番デプロイが Ready になるのを待つ。この時点で旧リンクと旧画面は使えなくなる（停止開始）。
3. 管理者ログインを確認する（`/login`）。
4. `02_lockdown.sql` → `03_revoke_old_links.sql` の順に実行する。
5. 管理画面の「設定 > 担当者」で全員の共有リンクを発行し、表示されたURLをコピーして各担当者へ送る（URLは発行時のみ表示）。**これは短時間の停止を許容して配布する簡略案**。再開前に外注者本人へ別の連絡手段（LINE/メール等）で到達確認し、未送達者には代替受付を案内する。リンクへの初回アクセス記録だけでは本人への送達を証明できない。
6. `verify.sql` を実行し、A・B・C・D・E・Hが0行、Fが3行、Gの `plaintext_tokens` が0であることを確認する。
7. SQL Editor の `verify.sql` による権限・RLS・関数・ビューの拒否を確認し、結果を記録したうえで `DB_PERMISSIONS_VERIFIED=yes` を設定して `node scripts/verify-cutover.mjs` を実行する（使い方はスクリプト冒頭）。**検証スクリプトはデータ変更リクエストを行わない**。不合格・未確認がないことを確認する。
8. 管理画面で日報の登録・編集・削除、確定月の拒否を確認する。外注者リンクで1件登録し、管理画面の「受領確認」が確認済みになることを確認する（停止終了）。

## 停止中の代替受付
外注者は「作業日・顧問先・作業種別・数量（または時間）・メモ」をLINEまたはメールで管理者へ送る。再開後、管理者が管理画面から入力する（登録元は管理者入力になる）。

## 復旧の考え方
- 公開権限（anon全開放）には戻さない。新しい画面・APIの不具合は修正してデプロイし直す（前方修正）。
- ログインできない場合: Vercel の `ADMIN_EMAIL` と Supabase の管理者アカウントのメールアドレスが一致しているか、パスワードを Supabase の管理画面で再設定できるかを確認する。
- 画面にデータが出ない場合: `SUPABASE_SERVICE_ROLE_KEY` が Production に設定され、再デプロイ済みかを確認する。
- データの破損が疑われる場合のみ、当日取得したバックアップから個別に復元する（自動復元機能はない）。

## 完了判定
- `verify.sql` における公開ロールの権限・RLS・ビュー/RPCの遮断結果、および `verify-cutover.mjs` がすべて合格。WARN/SKIPや未確認の項目を合格に読み替えない
- 管理者ログイン・日報の登録/編集/削除・確定月の拒否・外注者リンクでの登録が本番で確認済み
- 全外注者に新しいリンクが届き、受領確認（初回利用）が付いている
