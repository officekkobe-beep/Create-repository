# AI開発標準運用ルール（ChatGPT / AI Council / Claude / Claude Code）

更新日: 2026-11-22
対象: 本リポジトリの設計・機能追加・修正・リリース
優先事項: ユーザー既決事項、現行の実装と本番データ保護。矛盾がある場合は勝手に上書きせず報告する。

## 1. 役割と入口
- ChatGPT: 要望整理、既決事項の調査、仕様案、Claudeレビュー依頼・取得・反映、検収と次工程の管理。
- Claude（AI Council）: 設計への批判的レビュー、整合性・セキュリティ確認、重大問題の指摘。
- Claude Code: 確定仕様に沿ったコード修正、テスト、PR、必要なデプロイ確認。独自の大幅な仕様変更をしない。
- **重要な設計**（画面フロー、金額計算、データ構造、認証・権限、API、保存、重要な仕様変更）は、**ChatGPT案 → AI CouncilのClaudeレビュー → 指摘反映 → 必要なら再レビュー → ユーザー確認 → Claude Code実装**。
- 文言・色等の軽微変更はレビュー省略可。ただし単価・請求・RLS・月次確定に触れる変更は軽微扱いにしない。

## 2. AI Councilの正しい宛先
- 既存自動レビューキュー: `officekkobe-beep/ai-council-queue` の GitHub Issues。
- 自動処理識別子 `[AI_REVIEW_LOOP_V1]` をIssueタイトルに付し、Issue本文の冒頭にも `<!-- AI_REVIEW_LOOP_V1 -->` を入れる。
- Issueには目的、対象リポジトリ、既決事項、修正可能範囲、禁止事項、設計案、争点、期待するレビュー結果を書く。
- **アプリ側リポジトリに通常のIssueを作るだけではClaudeレビューにならない**。通常Issueは仕様の記録・参照先であり、レビューの宛先として代用しない。
- AI Council実行開始のコメントと、最終レビューコメント、Issueの状態を確認する。開始コメントのみではレビュー完了と報告しない。
- 自動化の状態が不明なら、同キューの過去の承認済みIssueとコメント構造を参照し、原因を調べる。自動処理が失敗・未起動なら「未実施／失敗／処理中」を区別する。
- Claudeの完了レビューが取得できない場合は、設計確定・実装着手と偽らない。既決の設計がすでに承認済みならそのレビュー番号・適用範囲を確認して利用する。

## 3. 状態管理と完了条件
各開発単位について、少なくとも次の状態を区別する:
1. 要件整理
2. ChatGPT設計案
3. Council依頼済み
4. Councilレビュー処理中
5. レビュー結果取得済み（承認／条件付き／差戻し）
6. 指摘反映済み／再レビュー待ち
7. ユーザー仕様確認済み
8. Claude Code実装中
9. テスト合格／不合格／未実施
10. PR作成・レビュー中
11. マージ済み
12. 本番反映済み
13. ユーザー画面確認済み

- **Issue作成＝レビュー完了ではない**。**PR作成＝本番反映ではない**。**build成功＝実動作検収ではない**。
- 各回答末尾の報告は「実際に完了したこと」「証拠URL/番号」「未完了」「次工程」を区別する。
- ユーザーが「進めて」「直して」と言った際、利用可能な連携で実行できる範囲は実行する。単なるコピペ指示書で中断しない。
- 実行環境が長時間稼働・常時監視を保証しない場合、継続監視できるかのように言わない。必要な場合は利用可能な通知／自動確認の設定を検討する。
- 重要な未決事項や不可逆な操作（本番SQL・既存仕様変更・データ削除・危険なマージ）はユーザー承認前に進めない。

## 4. Claude Codeへの実装指示テンプレート
レビュー完了後、以下を必ず含む:
- 目的・作るもの・対象画面
- 既決事項と**変えてはいけないもの**
- 対象ファイル・DB変更内容（実コード調査後）
- 工程分割（例: UI骨格→保存→計算→集計/出力→検収）
- 各工程の完了条件・テストケース・回帰テスト
- 誰が何を確認するか、PR・本番反映・ユーザー画面確認の区別
- 保留課題と戻し方

## 5. 本番データと既存機能の保護
- 本番の既存日報、顧問先、担当者、単価、外注者リンク、確定状態を初期化しない。
- Supabaseスキーマ変更前に全データバックアップ、SQL差分レビュー、追加対象の存在確認、実行後の確認を行う。**古い別クローンのschema.sqlは使わず最新の正本を確認**。
- `DROP TABLE`、`TRUNCATE`、無条件`DELETE FROM`のような破壊的SQLを通常の変更に含めない。
- 単価・売上・外注費・月次確定の変更は既存の請求計算・無料枠・外注費・対象年度・CSV・JSONバックアップに回帰テストを実施する。
- 外注者画面は金額・管理機能を表示しないだけでなく、DB/APIの権限を検証する。

## 6. 新しいチャットへの引継ぎ
- 本リポジトリの `CLAUDE.md` → 本ファイル → 関連Issue/PR → AI Council該当Issue（コメント含む）→ 最新の実装の順に確認する。
- 前の回答や記憶だけで「レビュー完了」「本番反映済み」を推定しない。GitHub側の状態を確認する。
- プロジェクトの既決事項はこの文書で上書きしない。既決の変更提案があれば理由と影響を提示してユーザー承認を取る。
